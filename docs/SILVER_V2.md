# Silver V2 — audited boilerplate removal (ruleset v2)

Silver V2 starts from a **checksum-verified Silver V1 report**, not from a new Bronze download.
Neither Bronze/Silver V1 nor Gold V1 is changed. Gold V2 is **not** generated by this command.

## Safety and limits

- Inspect standalone **tail-only** footer markers (copyright, powered by, comment forms, related-content labels and navigation).
- Keep the 55%-of-document tail boundary for candidate headings.
- Trim on an unmistakable strong footer marker **or** a standalone related-articles/recent-posts heading with **at least three title-like lines** and no bibliography/reference heading in the candidate suffix.
- An isolated "related articles" heading without corroborating list structure remains **review-only**. A list with references also remains for review.
- If the earliest candidate exceeds a safety limit, try a later strong marker; never silently relax the limits.
- Preserve at least 200 characters and remove no more than 35% of the document. Cases that exceed limits remain intact and are flagged.
- Retain source IDs/domain, recompute text length, preserve existing quality flags and append `silver_v2:cleaned`, `silver_v2:review`, or `silver_v2:guardrail`.
- Any duplicate full text produced by cleaning is rejected with its reason rather than silently entering Gold.
- This is a conservative heuristic, **not** complete HTML extraction. Some boilerplate survives, and false positives remain possible.
- Changes and removals have an audit JSONL (ID, class, action, signal, before/after lengths, short removed preview). Do not treat automatic flags as manually verified labels.

The dry-run does not write to Drive. A publishing run creates new **write-once** files under `02_silver/` and `05_reports/` with a suffix identifying the source checksum and cleaner configuration:

```text
02_silver/vtsnlp_silver_v2_<source-hash>_<config-hash>.jsonl
02_silver/vtsnlp_rejected_v2_<source-hash>_<config-hash>.jsonl
05_reports/silver_audit_v2_<source-hash>_<config-hash>.jsonl

```

The report includes input/accepted/rejected counts, removed characters, signal counts, source SHA256 and three output SHA256 checksums; `SilverReader` can verify the published V2 output.

**Do not automatically train on Silver V2 until the audit sample is reviewed.** When approved, use the pinned V2 report to create a separate Gold V2 snapshot. Compare the impact on validation using a sound evaluation protocol and leave the old benchmark immutable.

## Ruleset revision and comparison

The revised ruleset is `silver-v2-tail-v2`. V2 pipeline filenames include the ruleset in their configuration fingerprint, so publishing a new ruleset **does not overwrite** the already-published `silver-v2-tail-v1` snapshot.

Exploratory replay against the 50,000 text records in the pinned **Gold V1** snapshot (which retain the original Silver V1 text) yielded:

| Action | Published ruleset v1 | Revised ruleset v2 pilot |
| --- | ---: | ---: |
| Cleaned | 1,305 | 2,263 |
| Review | 1,145 | 299 |
| Guardrail | 75 | 139 |
| Unchanged | 47,475 | 47,299 |

The pilot counted **958 additional cleanable suffixes**, but **these are heuristic candidates, not verified true positives**. Evaluate the examples printed in the notebook before publication and sample unflagged records to estimate residual noise. Cleaning is not a substitute for manual labeling or source-aware HTML extraction.
